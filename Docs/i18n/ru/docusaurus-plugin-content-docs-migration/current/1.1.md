# Руководство по миграции: 1.0 → 1.1

Что поменять в проекте при переходе с **Aspid.MVVM 1.0.x** на **1.1.0**. Полный список изменений — на странице [Изменения](https://vpdpersonal.github.io/Aspid.MVVM/ru/changelog#v1-1-0).

Каждый перемещённый скрипт сохранил GUID в `.meta`, поэтому префабы, сцены и ScriptableObject не теряют ссылок. **Исходный код — теряет**: переименованные типы правятся поиском и заменой. У переименованных типов нет `[MovedFrom]`; слот `[SerializeReference]`, настроенный со старым именем типа, нужно прогнать через инструмент починки сериализованных ссылок или настроить заново.

---

## Кратко

1. Обновите редактор до Unity `6000.0.53f1` или новее.
2. Добавьте необязательные пакеты для используемых интеграций (§ 1).
3. Переименуйте типы по таблице § 2; остальное найдёт компилятор.
4. `view.Dispose()` и `view.DestroyView()` больше не уничтожают GameObject (§ 4.2).
5. Свои наследники `CollectionBinder<T>` реализуют шесть новых хуков (§ 4.4).
6. Заново настройте пороги `NumberCompareConverter` и фолбэки `ParseHtmlStringConverter` (§ 4.7).

## 4. Изменения поведения

### 4.1 `MonoView` стал конкретным

`MonoView` больше не `abstract`: список биндеров, валидация детей и `[RequireBinder]` живут в нём. Наследники продолжают работать; новые сериализуемые поля стартуют пустыми.

### 4.2 `Dispose()` и `DestroyView()` сохраняют GameObject

```csharp
// 1.0 — оба уничтожали GameObject
view.Dispose();
view.DestroyView();

// 1.1
view.Dispose();                   // только Deinitialize()
Object.Destroy(view.gameObject);  // если объект всё же нужно убрать

view.DestroyView();               // уничтожает только компонент View
view.DestroyViewAndGameObject();  // поведение 1.0
```

Оба метода-расширения возвращают `null` вместо исключения на уничтоженном View и вне play mode используют `DestroyImmediate`.

`DestroyView()` теперь уничтожает и ScriptableObject-представления. Для одной лишь очистки используйте `DisposeView()`. Для компонентов `DestroyView()` по-прежнему сохраняет GameObject; для его удаления используйте `DestroyViewAndGameObject()`.

Методы уничтожения теперь находятся в `ViewExtensions` в сборке ядра. Замените явные вызовы `MonoViewExtensions.DestroyView(view)` на `ViewExtensions.DestroyView(view)`. Синтаксис `view.DestroyView()` сохраняется.

### Очистка и уничтожение ViewModel

`MonoViewModel.Dispose()` больше не уничтожает компонент. `MonoViewModel` и `ScriptableViewModel` реализуют однократную очистку ресурсов через `IDisposable`. Перенесите реализацию `public override void Dispose()` в `protected override void OnDispose()`. Повторные и реентерабельные вызовы игнорируются, в том числе после исключения при очистке. Если ресурсов несколько, попытайтесь освободить каждый до сообщения об ошибках.

Очистка выполняется, когда Unity вызывает `OnDestroy()`; при переопределении нужно вызывать базовую реализацию. Сам `Dispose()` сохраняет Unity-объект. Флаг очистки в `ViewInitializer` также только освобождает ресурсы и не уничтожает внешний Unity-объект.

Используйте `DestroyViewModel()` для очистки и уничтожения компонента или ScriptableObject. `DestroyViewModelAndGameObject()` предназначен для случая, когда вызывающий код владеет всем GameObject. Оба метода выбрасывают `ArgumentNullException` для null и уничтоженных ViewModel. Для живой модели они пытаются уничтожить объект даже при ошибке очистки, затем передают исключение вызывающему коду. Для обычной C# ViewModel они выполняют только очистку, если она поддерживается. В Edit Mode уничтожение немедленное, в Play Mode отложенное.

`DestroyViewModelAndGameObject()` возвращает `void`. `DestroyViewModel()` возвращает сохранившийся GameObject. Используйте `DestroyViewModelSafely()` или `DestroyViewModelAndGameObjectSafely()`, если ViewModel может отсутствовать или быть уже уничтоженной. Обрабатывайте ошибки очистки в месте вызова. Методы `DestroyViewSafely()` и `DestroyViewAndGameObjectSafely()` пропускают отсутствующие View и передают ошибки очистки вызывающему коду. Для явных вызовов с аргументом типа теперь используйте перегрузки с интерфейсом.

Методы уничтожения теперь находятся в `ViewModelExtensions` в сборке ядра. Замените явные вызовы `MonoViewModelExtensions.DestroyViewModel(model)` на `ViewModelExtensions.DestroyViewModel(model)`. Синтаксис `model.DestroyViewModel()` сохраняется.

### 4.3 `MonoBinder.Bind()` на уже привязанном биндере

`Binder.Bind()` и `MonoBinder.Bind()` выбрасывают `InvalidOperationException` при повторной или рекурсивной привязке и сохраняют прежнее подключение.

Перегрузки `Safely` пропускают `null` вместо коллекции, `null`-биндеры и уничтоженные Unity-биндеры. Исключения получает вызывающий код. `BindSafely` останавливается при первой ошибке и сохраняет предыдущие привязки. `UnbindSafely` для коллекций пытается отвязать остальные биндеры и затем выбрасывает исходное исключение или `AggregateException` при нескольких ошибках.

Перенесите обязательные подписки из `OnBound` в новый `OnAttach`, а освобождение ресурсов из `OnUnbound` в `OnDetach`, включая вызовы `base`. `OnAttach` выполняется после `Adder.Add` и первого значения, но до перехода в `Bound`. `OnDetach` выполняется после снятия привязки, пока владелец ещё сохранён. Эти этапы установки и очистки должны допускать частичную инициализацию.

`OnBound` и `OnUnbound` теперь уведомляют о завершённом переходе. Ошибка в `OnBound` распространяется выше без отката установленной привязки. Из `OnBound` разрешена последовательность `Unbind → Bind`, а из `OnUnbound` сразу доступен новый `Bind`. `IsBound` равен `true` только в состоянии `Bound`; в `OnUnbinding` он уже `false`, хотя канал ещё позволяет отправить последнее значение. Владение и все ресурсы освобождаются до `OnUnbound`; после ошибки очистка продолжает остальные шаги и пробрасывает исходное исключение или `AggregateException` при нескольких ошибках.

`IBinder` теперь требует `bool IsBound { get; }`. Наследники `Binder` / `MonoBinder` уже реализуют его. Прямые реализации должны отражать завершённую привязку и сбрасывать состояние при начале очистки; ошибки установки освобождают частично приобретённые ресурсы. `OneTime` остаётся привязанным до `Unbind`. Ошибка уведомления после установки сама по себе не освобождает владельца.

`IBinder.Bind(IBinderAdder)` заменён на `Bind(in BindContext)`, а `Unbind()` на `Unbind(in UnbindContext)`. Передавайте один и тот же экземпляр владельца при привязке и очистке:

```csharp
binder.Bind(new BindContext(member, owner));
binder.Unbind(new UnbindContext(owner));
```

Владелец имеет тип `object`: им может быть View или составной binder.
`BindSafely(member, owner, name)` заменяется на `BindSafely(new BindContext(member, owner))`; сохранённый контекст передаётся как `in context`.
Замените `BindSafely(result, owner, name)` на `if (result.Adder is { } member) binder.BindSafely(new BindContext(member, owner));`.
`UnbindSafely(owner, name)` заменяется на `UnbindSafely(new UnbindContext(owner))`; все перегрузки принимают сохранённый `in context`.
Прямые реализации `IBinder` должны сохранять владельца и проверять его через `ReferenceEquals`, игнорируя чужую очистку. `Binder` / `MonoBinder` выполняют это автоматически. Повторный `Bind`, включая того же владельца, запрещён; новый владелец может приобрести binder после завершения очистки. Составной binder передаёт дочерним себя как владельца и освобождает их при собственной очистке. Debug Rebind сохраняет прежнего владельца.

Для одиночного биндера вызывайте `binder.UnbindSafely(in context)`, чтобы пропустить `null` или уничтоженный биндер. Расширения `Unbind` предназначены для коллекций и спанов.

Ошибки очистки собираются на уровнях `Binder` / `MonoBinder`, коллекций, групп `MonoView`, сгенерированной View и инициализаторов. Одна ошибка сохраняет свой экземпляр и stack trace; несколько возвращаются в `AggregateException`. Для вложенных агрегатов используйте `exception.Flatten().InnerExceptions`. Список ошибок создаётся только при второй ошибке; успешный путь не получает дополнительных аллокаций от агрегации. При неудачной установке `Bind` и инициализации View первоначальная ошибка сохраняет приоритет над ошибками отката.

Для `IEnumerable<T>` ошибка обхода может оставить часть биндеров необработанной.
`BindSafely` использует `foreach`, поэтому исключение из `Dispose()` имеет приоритет над ошибкой привязки или обхода.
`UnbindSafely` собирает обе ошибки в `AggregateException`.
Сгенерированные View откатывают инициализацию при ошибке биндера.

`ViewBindings` удалён. Генератор напрямую привязывает и освобождает фиксированный набор биндеров, без списка приобретённых экземпляров, обёрток учёта и записей попыток. Между `Initialize` и `Deinitialize` нельзя заменять binder-поля или менять состав коллекций; повторный обход должен возвращать те же экземпляры. Кеши binder-свойств и `[AsBinder]` сохраняются. Очистка продолжает работу после исключений и затем пробрасывает исходное исключение или `AggregateException` при нескольких ошибках.

### 4.4 Хуки `CollectionBinder<T>`

`CollectionBinder<T>` подписывается на `CollectionChanged` и добавляет шесть абстрактных хуков. Свой наследник обязан их реализовать; пустые тела дают поведение 1.0.

```csharp
protected abstract void OnAdded(T? newItem);
protected abstract void OnAdded(IReadOnlyList<T?>? newItems);
protected abstract void OnRemoved(T? oldItem);
protected abstract void OnRemoved(IReadOnlyList<T?>? oldItems);
protected abstract void OnReplaced(T? oldItem, T? newItem, int index);
protected abstract void OnMoved(T? oldItem, T? newItem, int oldStartingIndex, int newStartingIndex);
```

`CollectionMonoBinder<T>` сохранил `OnAdded(IReadOnlyCollection<T>)` / `OnReset()`, но теперь следит за коллекцией и перестраивается на каждом изменении.

### 4.5 `ViewInitializer`

Оба инициализатора отклоняют деинициализацию во время инициализации до освобождения приобретённых View. Перенесите очистку за пределы callbacks инициализации. При ошибке инициализации внутренний rollback сохраняется; отклонённый повторный вызов не меняет исходную ViewModel.

Резолв перенесён в `ViewInitializerBase`, `Resolve` контейнера стал `TryResolve` (неудачный резолв больше не бросает), добавлена стадия `InitializeStage.DiConstructor`. Стадия по умолчанию по-прежнему `Awake`. Сериализованные записи резолва сменили тип — перепроверьте `ViewInitializer` / `ViewInitializerManual` в инспекторе.

Генерируемые View логируют ошибки отдельных биндеров и продолжают подключать исправные. Исключения из lifecycle-hook самой View по-прежнему распространяются выше. Генерируемые View и оба инициализатора после ошибки откатывают приобретённые привязки, сбрасывают флаги инициализации и допускают повторную попытку. Ранее привязанные биндеры и View остаются у прежнего владельца; уже инициализированный слот View отклоняется без его деинициализации.

### 4.6 Биндеры

- **Режим уведомлений**: конструкторы биндеров значения принимают `notifyMode` перед существующими необязательными аргументами. Обновите позиционные вызовы или используйте именованные аргументы `converter:` и `mode:`. Передайте `NotifyMode.Always` создаваемым из кода биндерам Toggle и Slider, чтобы сохранить прежние уведомления. Сохранённые компоненты сохраняют прежнее поведение; новые Mono-биндеры начинают с `Never`.

  ```diff
  - new ToggleIsOnBinder(toggle, converter, BindMode.TwoWay)
  + new ToggleIsOnBinder(toggle, NotifyMode.Always, converter, BindMode.TwoWay)
  ```

- **Пути `[AddComponentMenu]`**: `Collections/…` → `Collection/…`, дефис → длинное тире (`Binder – ViewModel`). Обновите инструменты, сравнивающие пути меню.
- **Addressable-биндеры** получили опциональный `_seamlessSwap`; жизненный цикл загрузки использует раздельные current/pending handle. Перепроверьте наследников, переопределяющих установку ассета или освобождение.
- **Санитизация стала громкой**: `NaN` или бесконечность, записанные в биндер, ограничиваются и репортятся через `BinderLogger`. Конечное значение вне диапазона по-прежнему насыщается молча.
- **Обратная привязка конвертирует**: в `TwoWay` / `OneWayToSource` применяется `ConvertBack` конвертера. Уберите компенсацию отсутствующей обратной конверсии из ViewModel.
- **Bool-биндеры** несут слот `IConverter<bool, bool>` вместо `_isInvert`. Инверсию настройте заново через `BoolInvertConverter`; биндеры `*ByBind` сохранили флаг.
- **Новый `MonoBinder`**, включая runtime `AddComponent`, стартует в `DefaultMode`. Другой поддерживаемый режим можно задать через `binder.Mode` до привязки; изменение во время привязки или в привязанном состоянии бросает исключение. Сохранённые режимы `1`–`4` не меняются. Ранее неподдерживаемое сериализованное значение `0` теперь выбирает режим по умолчанию; пересохранять сцены и префабы не нужно.
- **Уничтоженный `MonoBinder`** отвязывается из `OnDestroy`; в переопределениях вызывайте `base.OnDestroy()`.

### 4.7 Конвертеры

- **Неверная конфигурация репортится при каждой конвертации** и возвращает настроенный фолбэк. Ожидайте новых ошибок в консоли от настроек, которые были молча сломаны.
- **`NumberCompareConverter`** (был `NumberToBoolConverter`): `Inequality` в 1.0 был инвертирован и теперь работает; порог `_value` расширен с `float` до `double`, поэтому каждый настроенный порог читается как `0` — настройте заново.
- **`ParseHtmlStringConverter`**: фолбэк переехал из `_defaultColor` в `_fallback` и настраивается заново; нераспознанный цвет теперь репортится.
- **`ValueToStringConverter<T>`** (был `GenericToString<TFrom>`): форматирование — виртуальный хук `Format(T value, string format)`; пустой или пробельный формат откатывается к `ToString()`. `FormatException` сдерживается, а не обрывает список подписчиков биндера.
- **Пробелы — это пусто**: каждый строковый конвертер считает строку из пробелов пустой.

### 4.8 `DynamicViewModel`

```csharp
var viewModel = new DynamicViewModel
{
    { "Title", "Hello" },
    { "Volume", 0.5f, BindMode.TwoWay }
};

IDynamicProperty<float> volume = viewModel.Get<float>("Volume");
volume.Value = 0.8f;
volume.ValueChanged += v => Debug.Log(v);
```

`Add<T>` возвращает тот же handle `IDynamicProperty<T>`. Все четыре `BindMode` живут на одном типе свойства; число свойств не ограничено.

### 4.9 `RelayCommand`

`RelayCommand.Empty` остаётся невыполнимым; `RelayCommand.EmptyExecution` выполним и ничего не делает.

`CreateCommandWithoutParameters*` теперь возвращает адаптер, который передаёт `CanExecuteChanged`, пока у него есть слушатели. `Execute` напрямую вызывает источник, поэтому у обёрнутого `RelayCommand` предикат проверяется один раз. Собственные реализации команд сохраняют свою политику выполнения. Строгая перегрузка сразу выбрасывает `ArgumentNullException(nameof(command))` при отсутствии источника; варианты `OrEmpty*` сохраняют прежние заглушки. Уберите ручную пересылку уведомлений, если она компенсировала прежнее ограничение адаптера.

### 4.10 Маркеры профайлера

Маркеры профайлера `DisposeView` и `DisposeViewModel` удалены. Для освобождения через фреймворк вызывайте `DisposeViewModel()` / `DisposeView()`, а для измерения более широкой операции создайте свой маркер. Маркеры пакета компилируются только под `ENABLE_PROFILER` без `ASPID_MVVM_UNITY_PROFILER_DISABLED`.

### 4.11 Фабрики исключений биндеров

`BinderInvalidCastException.Class/Struct` и `ReverseBinderInvalidCastException<T>.Class/Struct` теперь возвращают исключение без выбрасывания. Добавьте `throw`, если ваш код вызывал фабрику отдельной инструкцией:

```csharp
throw BinderInvalidCastException.Class<string>(binder);
throw ReverseBinderInvalidCastException<string>.Class(binder);
```

Существующие выражения с `throw` и блоки `catch` продолжают работать.

### 4.12 Валидация режимов привязки

| Прежний метод | Замена |
| --- | --- |
| `mode.IsOne()` | `mode.IsForwardOnly()` |
| `mode.IsTwo()` | `mode.IncludesReverse()` |
| `mode.IsNone()` | `mode == BindMode.None` |
| `mode.ThrowExceptionIfNone()` / `ThrowExceptionIfInvalid()` | `mode.EnsureValid()` |
| `mode.ThrowExceptionIfNotOne()` / `ThrowExceptionIfTwo()` | `mode.EnsureForwardOnly()` |
| `mode.ThrowExceptionIfNotForward()` | `mode.EnsureForward()` |
| `mode.ThrowExceptionIfNotTwo()` | `mode.EnsureReverse()` |
| `mode.ThrowExceptionIfMatches(excludedMode)` | `mode.EnsureNot(excludedMode)` |
| `mode.ThrowExceptionIfOne()` | `mode.EnsureReverse()`, если нужны обновления из View во ViewModel |
| `mode.ThrowExceptionIfNotMatches(expected)` | Явное сравнение с требуемым режимом |

`IsValid()` исключает `None` и неопределённые значения; `IncludesForward()` включает `OneWay`, `TwoWay` и `OneTime`. Свойства атрибутов `IsOne` и `IsTwo` сохраняют имена.

Конструкторы `Binder` теперь выбрасывают `ArgumentOutOfRangeException` для `None` и неопределённых режимов. `EnsureForwardOnly()` принимает только `OneWay` и `OneTime`, а `EnsureForward()` также принимает `TwoWay`. `EnsureReverse()` принимает `TwoWay` и `OneWayToSource`. `EnsureNot(excludedMode)` принимает любой допустимый режим, кроме указанного. У каждой проверки одна сигнатура, при нарушении условия выбрасывается исключение; старые имена проверок удалены.

Конструкторы атрибутов отклоняют null-списки и недопустимые элементы; пустой список сохраняет прежний смысл. Генерируемые ограничения учитывают обе группы, а некорректные override получают диагностику `ASPIDSB006`.

Сериализованные значения от `0` до `4` не меняются. `MonoBinder` по-прежнему разрешает внутреннее ненастроенное значение `None` через `DefaultMode`.

### 4.13 Запросы и атрибуты ViewModel

`FindBindableMemberParameters` остаётся `readonly ref struct`. Конструктор отклоняет null, пустые и пробельные ID. Сгенерированные ViewModel, `DynamicViewModel` и `EmptyViewModel` также отклоняют запрос `default`. Обе перегрузки `DisposeViewModel` отклоняют null и уничтоженные Unity-объекты через `ArgumentNullException`.

`[Access(access)]` теперь сохраняет аргумент конструктора в `Get` и `Set`; именованные аргументы переопределяют отдельные аксессоры. Недопустимые значения доступа и явные режимы привязки отклоняются. `BindAttribute.Mode` возвращает явный режим или null при автоматическом определении. Метаданные Editor следуют тем же правилам режима, что и генератор.

Диагностики генератора заменяют молчаливое игнорирование ошибочных настроек:

| ID | Настройка |
| --- | --- |
| `ASPIDVM001` | Недопустимые или конфликтующие режимы привязки |
| `ASPIDVM002` | Недопустимая видимость аксессоров |
| `ASPIDVM003` | Пустая или отсутствующая цель `BindAlso` |
| `ASPIDVM004` | Отсутствующий или несовместимый предикат `CanExecute` |
| `ASPIDVM005` | Повторный `RelayCommand` или неподдерживаемая сигнатура команды |
| `ASPIDVM006` (предупреждение) | Привязка или зависимость пропущена, поскольку член её не поддерживает |

Исправьте ошибки перед использованием сгенерированной ViewModel. На методе разрешён один `[RelayCommand]`; неверный предикат никогда не превращается в команду без проверки.

### 4.14 Жизненный цикл View и атрибуты биндеров

Сгенерированные View игнорируют повторный `Deinitialize()`, пока очистка уже выполняется. Вызов во время инициализации выбрасывает `InvalidOperationException`; перенесите его из хуков инициализации. Очистка по-прежнему освобождает остальные биндеры и пробрасывает исходное исключение или `AggregateException` при нескольких ошибках. Неудачная попытка привязки больше не удаляет учёт успешных вложенных привязок.

Сгенерированные View защищают инициализацию и очистку от конфликтующих повторных вызовов. `DisposeView<T>` требует ссылочный тип. `DeinitializeView`, `Reinitialize` и обе перегрузки `DisposeView` отклоняют null-View через `ArgumentNullException`, как и `DisposeViewModel`. Эти методы также отклоняют уничтоженные Unity-объекты. Для необязательной или уничтоженной View используйте `view.DisposeViewSafely()`. Возвращаемый null означает, что у существующей View не было ViewModel; `Reinitialize(null)` по-прежнему только деинициализирует её. Эти методы не освобождают ViewModel автоматически. Если `Reinitialize` завершается ошибкой при инициализации сгенерированной View, она остаётся отвязанной; прежняя ViewModel не восстанавливается и не освобождается.

`[View]` применяется только к классам. Класс без `partial` или со `static` получает `ASPIDVIEW003`. Неверный тип `[AsBinder]` получает `ASPIDVIEW001`; недопустимый массив аргументов, нечитаемая цель или несовместимый конструктор получают `ASPIDVIEW002`. Тип биндера должен быть доступным, неабстрактным, закрытым и реализовывать `IBinder`.

Аргументы конструктора сохраняют свои C#-типы и экранирование независимо от текущей культуры. `nameof(X)` по-прежнему передаёт член View `X`. Null-массив `params` недопустим; для одного null-аргумента конструктора используйте `(object)null`.

## 5. Свои биндеры в 1.1

- **Сериализуемый близнец генерируется.** Пишите `MonoBinder`-половину, помечайте её `[GenerateSerializableBinder]` — `{Name}Binder` генерируется над соответствующим `Target*Binder`. Близнец, уже существующий по имени, не трогается. Для атрибута подключите пространство имён `Aspid.MVVM`. Если регистрируете генераторы Roslyn вручную, подключите `Aspid.MVVM.Unity.Generators.dll`.
- **Базы свойств несут конвертер.** `TargetBinder<TTarget, TProperty>` и `ComponentMonoBinder<TComponent, TProperty>` держат слот `[SerializeReference] IConverter<TProperty, TProperty>`; поверх них — типизированные `Target{Int,Float,Object}Binder<TTarget>` и `Component{Int,Float,Object}MonoBinder<TComponent>`.
- **Числовые и векторные перегрузки приходят из интерфейсов.** `IIntBinder`, `ILongBinder`, `IFloatBinder`, `IDoubleBinder`, `IVector2Binder`, `IVector3Binder`, `IColorBinder`, `IRotationBinder` дают дополнительные `SetValue` как default-члены интерфейса; значения вне диапазона насыщаются. Доступны только через интерфейс: `((IBinder<float>)binder).SetValue(5f)`.
- **Один обратный канал для чисел.** `INumberReverseBinder` пробрасывает `IReverseBinder<int/long/float/double>.ValueChanged` в `NumberReverseChannel`, который держит биндер; подписка через `((IReverseBinder<float>)binder).ValueChanged`.
- **`BinderMath` называет вызывающего.**

```csharp
Target.pitch = this.SafeClamp(value, -3f, 3f, Target);            // внутри биндера
if (!this.RequireFinite(value, Target)) return;                   // вместо молчаливого IsFinite
value = BinderMath.SafeClamp(typeof(MyHelper), value, 0f, 1f);    // внутри статического хелпера
```

## Подписки слайдера UI Toolkit и владение материалами

`ElementSliderValueMonoBinder` теперь поддерживает обратные каналы `int`, `long`, `float` и `double`. Замените прямые подписки `sliderBinder.ValueChanged` на `((IReverseBinder<float>)sliderBinder).ValueChanged` (либо числовой тип вашей ViewModel). Обычные привязки ViewModel менять не нужно.

Биндеры материалов Renderer освобождают созданные копии при отвязке или уничтожении. При прямом вызове `MaterialInstanceConverter.Convert` вызывайте `Dispose` конвертера, когда его копии больше не нужны.
