# Migration Guide: 1.0 → 1.1

What to change in a project moving from **Aspid.MVVM 1.0.x** to **1.1.0**. The full list of changes is in the [changelog](https://vpdpersonal.github.io/Aspid.MVVM/changelog#v1-1-0).

Every relocated script kept its `.meta` GUID, so prefabs, scenes and ScriptableObjects keep their references. **Source code does not** — renamed types are a search-and-replace job. Renamed types carry no `[MovedFrom]`; a `[SerializeReference]` slot authored with an old type name needs the serialized-reference repair tool or re-authoring.

---

## TL;DR

1. Upgrade the Editor to Unity `6000.0.53f1` or newer.
2. Add optional packages for the integrations you use (§ 1).
3. Rename types from the table in § 2; the compiler finds the rest.
4. `view.Dispose()` and `view.DestroyView()` no longer destroy the GameObject (§ 4.2).
5. Custom `CollectionBinder<T>` subclasses implement six new hooks (§ 4.4).
6. Re-author `NumberCompareConverter` thresholds and `ParseHtmlStringConverter` fallbacks (§ 4.7).

---

## 1. Project and packages

- **Unity `6000.0.53f1`** is the minimum; the Editor project is on `6000.6.5f1`.
- FastTools is required; Collections remains optional. Git dependencies are not auto-resolved. Without FastTools, MVVM assemblies are excluded from compilation:

```json
"tech.aspid.collections": "https://github.com/VPDPersonal/Aspid.Collections.git#upm/1.1.1",
"tech.aspid.fasttools": "https://github.com/VPDPersonal/Aspid.FastTools.git#upm-preview/1.0.0-rc.9"
```

- `Aspid.Collections` no longer ships inside the package. Assembly (`Aspid.Collections.Observable`) and namespaces are unchanged.
- The framework moved from `Assets/Plugins/Aspid/MVVM/` to the UPM package `Packages/tech.aspid.mvvm/`. Update path constants and CI scripts; asset references survive.
- Assemblies `Aspid.MVVM.StarterKit.Unity` and `Aspid.MVVM.StarterKit.Unity.Editor` merged into `Aspid.MVVM.StarterKit` and `Aspid.MVVM.StarterKit.Editor`. Fix `.asmdef` references; the namespace `Aspid.MVVM.StarterKit` is unchanged.
- `SerializeReferenceDropdown` is no longer a dependency; `[SerializeReference]` fields are drawn by the FastTools type picker.

## 4. Behaviour changes

### 4.1 `MonoView` is concrete

`MonoView` is no longer `abstract`: the binder list, child validation and `[RequireBinder]` live on it. Subclasses keep working; the new serialized fields start empty.

### 4.2 `Dispose()` and `DestroyView()` keep the GameObject

```csharp
// 1.0 — both destroyed the GameObject
view.Dispose();
view.DestroyView();

// 1.1
view.Dispose();                   // Deinitialize() only
Object.Destroy(view.gameObject);  // if you still want the object gone

view.DestroyView();               // destroys only the View component
view.DestroyViewAndGameObject();  // the 1.0 behaviour
```

Both extension methods return `null` instead of throwing on a destroyed View and use `DestroyImmediate` outside play mode.

`DestroyView()` now destroys ScriptableObject views too. Use `DisposeView()` when only cleanup is needed. For components, `DestroyView()` still preserves the GameObject; use `DestroyViewAndGameObject()` to remove it.

The destruction extensions now live in `ViewExtensions` in the core assembly. Update explicit calls such as `MonoViewExtensions.DestroyView(view)` to `ViewExtensions.DestroyView(view)`. Extension syntax such as `view.DestroyView()` stays the same.

### ViewModel disposal and destruction

`MonoViewModel.Dispose()` no longer destroys the component. Both `MonoViewModel` and `ScriptableViewModel` implement one-time resource cleanup through `IDisposable`. Move `public override void Dispose()` implementations to `protected override void OnDispose()`. Repeated and reentrant calls are ignored, including after a cleanup exception. If cleanup owns several resources, attempt to release all of them before reporting failures.

Cleanup runs when Unity invokes `OnDestroy()`; overrides must call the base implementation. `Dispose()` itself preserves the Unity object. `ViewInitializer`'s disposal flag also only releases resources: it does not destroy an externally assigned Unity object.

Use `DestroyViewModel()` to dispose and destroy the component or ScriptableObject. Use `DestroyViewModelAndGameObject()` when the caller owns the entire GameObject. Both skip null or destroyed ViewModels. Both attempt destruction even if disposal fails and then propagate the cleanup failure. For managed ViewModels, they only dispose when supported. Destruction is immediate in Edit Mode and deferred in Play Mode.

`DestroyViewModelAndGameObject()` returns `void`. `DestroyViewModel()` returns the surviving GameObject. Use `DestroyViewModelSafely()` or `DestroyViewModelAndGameObjectSafely()` to log cleanup failures. The View counterparts are `DestroyViewSafely()` and `DestroyViewAndGameObjectSafely()`. Explicit generic destruction calls now use the interface overloads.

The destruction extensions now live in `ViewModelExtensions` in the core assembly. Update explicit calls such as `MonoViewModelExtensions.DestroyViewModel(model)` to `ViewModelExtensions.DestroyViewModel(model)`. Extension syntax such as `model.DestroyViewModel()` stays the same.

### 4.3 `MonoBinder.Bind()` on a bound binder

`Binder.Bind()` and `MonoBinder.Bind()` throw `InvalidOperationException` on repeated or reentrant binding and preserve the original binding. Use `BindSafely` / `UnbindSafely` to report binder exceptions without propagating them; single-binder and collection overloads follow the same policy.

Move required subscription setup from `OnBound` to the new `OnAttach`, and resource cleanup from `OnUnbound` to `OnDetach`, including `base` calls. `OnAttach` runs after `Adder.Add` and the first value but before entering `Bound`. `OnDetach` runs after member removal while the owner is still retained. Installation cleanup must tolerate partially initialized resources.

`OnBound` and `OnUnbound` now notify after the state transition completes. An exception from `OnBound` propagates without rolling back the established binding. `OnBound` may perform `Unbind → Bind`, and `OnUnbound` may immediately start a new `Bind`. `IsBound` is true only in `Bound`; it is already false during `OnUnbinding`, although the channel can still send a last value. Ownership and resources are released before `OnUnbound`; cleanup continues after failures and rethrows the original exception or an `AggregateException` for multiple failures.

`IBinder` now requires `bool IsBound { get; }`. Existing subclasses of `Binder` / `MonoBinder` already satisfy it. Direct implementations must reflect a completed binding and clear the state when cleanup starts; installation failures release partially acquired resources. `OneTime` remains bound until `Unbind`. A notification failure after installation does not itself release ownership.

`IBinder.Bind(IBinderAdder)` becomes `Bind(in BindContext)`, and `Unbind()` becomes `Unbind(in UnbindContext)`. Pass the same owner instance when binding and cleaning up:

```csharp
binder.Bind(new BindContext(member, owner));
binder.Unbind(new UnbindContext(owner));
```

The owner is an `object`, so a View or composite binder can own a binding. `BindSafely(member, owner, name)` becomes `BindSafely(new BindContext(member, owner), name)`; pass a stored context as `in context`. Lookup overloads retain `result` and `owner`. `UnbindSafely(owner, name)` becomes `UnbindSafely(new UnbindContext(owner), name)`; all overloads accept a stored `in context`. Binding and cleanup diagnostics use the owner from their context. Direct `IBinder` implementations must retain the owner and compare it through `ReferenceEquals`, ignoring foreign cleanup. `Binder` / `MonoBinder` do this automatically. Repeated `Bind`, including the same owner, is rejected; another owner can acquire the binder after cleanup finishes. A composite binder passes itself as its children's owner and releases them during its own cleanup. Debug Rebind preserves the original owner.

For a scalar binder, call `binder?.Unbind(in context)` through `IBinder`; `Unbind` extensions are only for arrays, lists and `IEnumerable`. `Unbind` and `UnbindSafely` are kept in `BinderExtensions.Unbind.cs`.

Cleanup errors are collected across `Binder` / `MonoBinder`, collections, `MonoView` groups, generated Views and initializers. One failure retains its instance and stack trace; multiple failures are reported in an `AggregateException`. Use `exception.Flatten().InnerExceptions` for nested aggregates. The error list is created only for the second failure, so aggregation adds no allocations on the successful path. Failed `Bind` installation and View initialization preserve the original failure over rollback failures.

`BindSafely(IEnumerable<T>)` and `UnbindSafely(IEnumerable<T>)` now retain both an enumeration failure and a failure from the enumerator's `Dispose` in an `AggregateException`, instead of losing the earlier failure. A single failure keeps its original instance and stack trace. Binder failures are still logged individually, and earlier successful operations are not rolled back.

`ViewBindings` is removed. The generator binds and releases a fixed binder set directly, without an acquired-instance list, tracking wrappers or attempt records. Do not replace binder fields or change collection contents between `Initialize` and `Deinitialize`; repeated enumeration must return the same instances. Binder property and `[AsBinder]` caches remain. Cleanup continues after exceptions and then rethrows the original failure or an `AggregateException` for multiple failures.

### 4.4 `CollectionBinder<T>` hooks

`CollectionBinder<T>` subscribes to `CollectionChanged` and adds six abstract hooks. A custom subclass must implement them; empty bodies restore the 1.0 behaviour.

```csharp
protected abstract void OnAdded(T? newItem);
protected abstract void OnAdded(IReadOnlyList<T?>? newItems);
protected abstract void OnRemoved(T? oldItem);
protected abstract void OnRemoved(IReadOnlyList<T?>? oldItems);
protected abstract void OnReplaced(T? oldItem, T? newItem, int index);
protected abstract void OnMoved(T? oldItem, T? newItem, int oldStartingIndex, int newStartingIndex);
```

`CollectionMonoBinder<T>` keeps `OnAdded(IReadOnlyCollection<T>)` / `OnReset()`, but now follows the collection and rebuilds on every change.

### 4.5 `ViewInitializer`

Both initializers reject deinitialization during initialization before releasing any acquired views. Move cleanup out of initialization callbacks. Internal rollback still runs when initialization fails; a rejected reentrant call preserves the original ViewModel.

Resolution moved into `ViewInitializerBase`, container `Resolve` became `TryResolve` (a failed resolve no longer throws), and `InitializeStage.DiConstructor` was added. The default stage is still `Awake`. The serialized resolution entries changed type — re-check `ViewInitializer` / `ViewInitializerManual` in the Inspector.

Generated Views log individual binder failures and continue initializing healthy binders. Exceptions from View lifecycle hooks still propagate. Generated Views and both initializers roll back acquired bindings after an initialization exception, clear initialization guards and permit another attempt. Preexisting bindings and Views remain with their original owner; a View slot that is already initialized is rejected without deinitializing it.

### 4.6 Binders

- **Notify mode**: value binder constructors insert `notifyMode` before the existing optional arguments. Update positional calls or use named `converter:` and `mode:` arguments. Pass `NotifyMode.Always` to code-created Toggle and Slider binders to keep their former notifications. Saved components keep their previous behavior; newly added Mono binders start with `Never`.

  ```diff
  - new ToggleIsOnBinder(toggle, converter, BindMode.TwoWay)
  + new ToggleIsOnBinder(toggle, NotifyMode.Always, converter, BindMode.TwoWay)
  ```

- **`[AddComponentMenu]` paths**: `Collections/…` → `Collection/…`, hyphen → en dash (`Binder – ViewModel`). Update tooling that matches menu paths.
- **Addressable binders** gained an opt-in `_seamlessSwap`; the load lifecycle uses separate current/pending handles. Re-check subclasses that override the asset-set or release flow.
- **Sanitising is loud**: a `NaN` or infinity written to a binder is clamped and reported through `BinderLogger`. A finite out-of-range value still saturates silently.
- **Reverse binding converts**: in `TwoWay` / `OneWayToSource` a converter's `ConvertBack` is applied. Remove any compensation your ViewModel did for the missing reverse conversion.
- **Bool binders** carry an `IConverter<bool, bool>` slot instead of `_isInvert`. Re-author inversion by picking `BoolInvertConverter`; `*ByBind` binders keep the flag.
- **A new `MonoBinder`**, including runtime `AddComponent`, starts in its `DefaultMode`. Set `binder.Mode` before binding to choose another supported mode; changes during binding or while bound throw. Saved mode values `1`–`4` remain unchanged. The previously unsupported serialized `0` now selects the default; no scene or prefab rewrite is required.
- **A destroyed `MonoBinder`** unbinds from `OnDestroy`; call `base.OnDestroy()` in overrides.

### 4.7 Converters

- **Misconfiguration reports on every conversion** and returns an authored fallback. Expect new console errors from setups that were silently broken.
- **`NumberCompareConverter`** (was `NumberToBoolConverter`): `Inequality` was inverted in 1.0 and now works; the `_value` threshold widened from `float` to `double`, so every authored threshold reads back as `0` — re-author it.
- **`ParseHtmlStringConverter`**: the fallback moved from `_defaultColor` to `_fallback` and must be re-authored; an unparsable colour is now reported.
- **`ValueToStringConverter<T>`** (was `GenericToString<TFrom>`): formatting is the virtual `Format(T value, string format)` hook; a blank or whitespace format falls back to `ToString()`. A `FormatException` is contained instead of cutting the binder subscriber list.
- **Whitespace is blank**: every string converter treats a whitespace-only string as empty.

### 4.8 `DynamicViewModel`

```csharp
var viewModel = new DynamicViewModel
{
    { "Title", "Hello" },
    { "Volume", 0.5f, BindMode.TwoWay }
};

IDynamicProperty<float> volume = viewModel.Get<float>("Volume");
volume.Value = 0.8f;
volume.ValueChanged += v => Debug.Log(v);
```

`Add<T>` returns the same `IDynamicProperty<T>` handle. All four `BindMode`s live on one property type; the number of properties is unlimited.

### 4.9 `RelayCommand`

`RelayCommand.Empty` stays non-executable; `RelayCommand.EmptyExecution` is executable and does nothing.

`CreateCommandWithoutParameters*` now returns an adapter that forwards `CanExecuteChanged` while it has listeners. It forwards `Execute` directly to the source, so a wrapped `RelayCommand` checks its predicate once. Custom command implementations retain their own execution policy. The strict overload throws `ArgumentNullException(nameof(command))` immediately for a missing source; `OrEmpty*` overloads keep their fallbacks. Remove any manual forwarding that was added to compensate for the former adapter limitation.

### 4.10 Profiler markers

The `DisposeView` and `DisposeViewModel` profiler markers were removed. Call `DisposeViewModel()` / `DisposeView()` to dispose through the framework, or create your own marker when measuring a larger operation. Package markers are compiled only under `ENABLE_PROFILER` without `ASPID_MVVM_UNITY_PROFILER_DISABLED`.

### 4.11 Binder exception factories

`BinderInvalidCastException.Class/Struct` and `ReverseBinderInvalidCastException<T>.Class/Struct` now return the exception without throwing it. Add `throw` if custom code called a factory as a statement:

```csharp
throw BinderInvalidCastException.Class<string>(binder);
throw ReverseBinderInvalidCastException<string>.Class(binder);
```

Existing `throw` expressions and `catch` clauses keep working.

### 4.12 Binding mode validation

| Previous helper | Replacement |
| --- | --- |
| `mode.IsOne()` | `mode.IsForwardOnly()` |
| `mode.IsTwo()` | `mode.IncludesReverse()` |
| `mode.IsNone()` | `mode == BindMode.None` |
| `mode.ThrowExceptionIfNone()` / `ThrowExceptionIfInvalid()` | `mode.EnsureValid()` |
| `mode.ThrowExceptionIfNotOne()` / `ThrowExceptionIfTwo()` | `mode.EnsureForwardOnly()` |
| `mode.ThrowExceptionIfNotForward()` | `mode.EnsureForward()` |
| `mode.ThrowExceptionIfNotTwo()` | `mode.EnsureReverse()` |
| `mode.ThrowExceptionIfMatches(excludedMode)` | `mode.EnsureNot(excludedMode)` |
| `mode.ThrowExceptionIfOne()` | `mode.EnsureReverse()` when reverse updates are required |
| `mode.ThrowExceptionIfNotMatches(expected)` | Compare with the required mode explicitly |

`IsValid()` excludes `None` and undefined values; `IncludesForward()` includes `OneWay`, `TwoWay` and `OneTime`. Attribute properties `IsOne` and `IsTwo` keep their names.

`Binder` constructors now throw `ArgumentOutOfRangeException` for `None` or undefined modes. `EnsureForwardOnly()` accepts only `OneWay` and `OneTime`; `EnsureForward()` also accepts `TwoWay`. `EnsureReverse()` accepts `TwoWay` and `OneWayToSource`. `EnsureNot(excludedMode)` accepts any valid mode except the specified one. Each guard has one signature and throws on failure; the old guard names are removed.

Attribute constructors reject null lists and invalid entries; an empty list retains its previous meaning. Generated mode restrictions now include both groups and report invalid overrides as `ASPIDSB006`.

The serialized values `0` to `4` are unchanged. `MonoBinder` still resolves its internal unconfigured `None` value through `DefaultMode`.

### 4.13 ViewModel queries and attributes

`FindBindableMemberParameters` remains a `readonly ref struct`. Its constructor rejects null, empty and whitespace IDs. Generated ViewModels, `DynamicViewModel` and `EmptyViewModel` also reject `default` queries. Both `DisposeViewModel` overloads reject null and destroyed Unity objects with `ArgumentNullException`.

`[Access(access)]` now retains the constructor value in both `Get` and `Set`; named arguments override each accessor. Invalid access values and explicit binding modes are rejected. `BindAttribute.Mode` exposes the explicit mode, or null when it is inferred. Editor metadata follows the same mode rules as the generator.

Generator diagnostics replace silent configuration failures:

| ID | Configuration |
| --- | --- |
| `ASPIDVM001` | Invalid or conflicting binding modes |
| `ASPIDVM002` | Invalid accessor visibility |
| `ASPIDVM003` | Empty or missing `BindAlso` target |
| `ASPIDVM004` | Missing or incompatible `CanExecute` predicate |
| `ASPIDVM005` | Duplicate `RelayCommand` or unsupported command signature |
| `ASPIDVM006` (warning) | A binding or dependency is skipped because the member cannot support it |

Fix errors before using the generated ViewModel. Only one `[RelayCommand]` is allowed per method; an invalid predicate never becomes an unguarded command.

### 4.14 View lifecycle and binder attributes

Generated Views ignore repeated `Deinitialize()` calls while cleanup is already running. Calling it during initialization throws `InvalidOperationException`; move that call out of initialization hooks. Cleanup still releases remaining binders and reports its original failure or an `AggregateException` for multiple failures. A failed binding attempt no longer discards ownership of successful nested bindings.

Generated Views guard initialization and cleanup against conflicting reentrant calls. Call `view.DeinitializeView()` without an explicit type argument. `DisposeView<T>` requires a reference type. `Reinitialize`, `DeinitializeView` and both `DisposeView` overloads reject a null View with `ArgumentNullException`, matching `DisposeViewModel`. These methods also reject destroyed Unity objects. Use `view.DisposeViewSafely()` for optional or destroyed Views. A null return means the existing View had no ViewModel; `Reinitialize(null)` still only deinitializes it. These helpers do not automatically dispose their ViewModels. If `Reinitialize` fails while initializing a generated View, that View is left detached; the previous ViewModel is not restored or disposed.

`[View]` targets classes only. Non-partial or static classes report `ASPIDVIEW003`. Invalid `[AsBinder]` types report `ASPIDVIEW001`; invalid argument arrays, unreadable targets or incompatible constructors report `ASPIDVIEW002`. The binder type must be accessible, non-abstract, closed and implement `IBinder`.

Constructor arguments retain their C# types and escaping independently of the current culture. `nameof(X)` still passes the View member `X`. A null `params` argument array is invalid; use `(object)null` to pass one null constructor argument.

## 5. Writing custom binders in 1.1

- **Serializable twin is generated.** Write the `MonoBinder` half, mark it `[GenerateSerializableBinder]`, and `{Name}Binder` is emitted over the matching `Target*Binder`. A twin that already exists by name is left alone.
- **Property bases carry the converter.** `TargetBinder<TTarget, TProperty>` and `ComponentMonoBinder<TComponent, TProperty>` hold a `[SerializeReference] IConverter<TProperty, TProperty>` slot; typed bases `Target{Int,Float,Object}Binder<TTarget>` and `Component{Int,Float,Object}MonoBinder<TComponent>` sit on top.
- **Numeric and vector overloads come from interfaces.** `IIntBinder`, `ILongBinder`, `IFloatBinder`, `IDoubleBinder`, `IVector2Binder`, `IVector3Binder`, `IColorBinder`, `IRotationBinder` supply the extra `SetValue` overloads as default interface members; out-of-range values saturate. They are reachable only through the interface: `((IBinder<float>)binder).SetValue(5f)`.
- **One reverse channel for numbers.** `INumberReverseBinder` bridges `IReverseBinder<int/long/float/double>.ValueChanged` to a `NumberReverseChannel` the binder holds; subscribe via `((IReverseBinder<float>)binder).ValueChanged`.
- **`BinderMath` names the caller.**

```csharp
Target.pitch = this.SafeClamp(value, -3f, 3f, Target);            // inside a binder
if (!this.RequireFinite(value, Target)) return;                   // replaces a silent IsFinite guard
value = BinderMath.SafeClamp(typeof(MyHelper), value, 0f, 1f);    // inside a static helper
```

## UI Toolkit slider subscriptions and material ownership

`ElementSliderValueMonoBinder` now supports `int`, `long`, `float` and `double` reverse channels. Replace direct `sliderBinder.ValueChanged` subscriptions with `((IReverseBinder<float>)sliderBinder).ValueChanged` (or the numeric type used by your ViewModel). Standard ViewModel bindings need no changes.

Renderer material binders release their instance copies on unbind or destruction. If you call `MaterialInstanceConverter.Convert` directly, dispose that converter when its copies are no longer needed.
